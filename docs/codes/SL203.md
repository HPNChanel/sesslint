# SL203: Unknown side-effect state

## Overview

- **Code**: `SL203`
- **Category**: `checkpoint`
- **Default Severity**: `error`
- **Default Repairability**: `manual`
- **Summary**: Repair would require assuming whether execution occurred.

## Invariant

Automated repair must never make unverified assumptions regarding whether an external side effect occurred.

## Cause

A tool call executed an unconfirmed or unmonitored external action (e.g. database write, payment API, shell command) without durable result.

## False-Positive Notes

Read-only tools mistakenly classified as side-effecting.

`codex-rollout` reports `adapter-not-applicable` and never emits SL203:
the format has no checkpoint mechanism (the adapter produces no
checkpoint-kind events), so "compaction without a subsequent checkpoint"
is vendor-normal operation rather than provable unsafe continuation —
on a real corpus this fired on ~93% of compacted files.

## Recipe or Manual Path

Automated repair always abstains when SL203 is present — under both policies. A single SL203 finding hard-blocks the entire plan (`SL203-refusal`), including steps targeting unrelated findings; the planner emits zero steps. No recipe handles SL203 directly (`side-effect-unknown-truncate` applies to `SL102` dangling calls, and even it cannot run while an SL203 finding exists). The only path is manual: the operator must establish whether the external action actually executed, edit the session accordingly, and re-run `sesslint check`.

Policy: *Conservative policy hard stop: automated repair must abstain when side effects are unknown.*

## Example

```json
tool_call(tool="deploy_production", params={...}) with no confirmation or result.
```
