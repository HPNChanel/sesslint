# SL304: Mid-file schema drift

## Overview

Flags records whose format signature or schema-version marker changes
mid-stream. A single session file should declare one schema generation;
when the markers or the envelope `type` vocabulary switch partway
through, the file was either spliced (two exports appended together) or
records an unrecorded format migration (vendor upgrade mid-conversation).

SL304 is **detection-only diagnostics**: it never blocks checking and it
never guesses which schema generation a record belongs to.

## Invariant

A session ledger declares one format and one schema generation. Every
record in the stream must belong to that generation — or the file must
be treated as two ledgers concatenated.

## Cause

- A record's envelope `type` is discriminative for a different vendor
  format (e.g. a `turn_context` or `compacted` record inside a
  claude-code-jsonl stream). Only types that uniquely identify one
  format count — shared vocabulary (`user`, `assistant`, `message`,
  `compaction`, …) never fires.
- A schema-version marker changes mid-stream while both the previous
  and the observed value are individually supported (e.g.
  `schemaVersion: "1"` → `schemaVersion: "0.1"`).

## False-Positive Notes

- **Application-version bumps are not drift.** Fields documented as
  application releases (e.g. `version: "2.0.30"` → `"2.1.0"` in
  claude-code-jsonl) share the same record grammar and are never
  observed — only explicit schema markers are.
- **Supported → unsupported transitions emit SL301, not SL304.** When
  any unsupported version marker appears in the file, SL301 fires once
  and all SL304 output for that file is suppressed — the unsupported
  version already fails detection and reporting both would double-report
  the same root cause.
- **Ordinary type-set variation never fires.** Unknown or vendor-specific
  types outside the discriminative table produce at most SL302 (unknown
  critical record) — SL304 requires the type to identify a *specific
  other* format.
- Legitimate mid-session vendor upgrades do exist; this is why the
  severity is `warning`, not `error`.

## Recipe or Manual Path

1. Identify the first record whose marker/signature differs (the
   finding's `record_index` and `line` give the position).
2. Check whether the file was spliced: the drift point usually splits
   the file into two coherent halves. If so, split it into two files and
   check each separately.
3. If the vendor genuinely migrated mid-session, keep the file as-is —
   the warning is informational; the records still parse.

## Example

```jsonc
// finding evidence (content-free)
{
  "drift_kind": "signature",            // or "version"
  "previous_marker": "claude-code-jsonl",
  "observed_marker": "turn_context",
  "observed_format": "codex-rollout",   // signature kind only
  "field": "type",                      // or e.g. "schemaVersion"
  "record_index": 42
}
```

At most 8 distinct transitions are reported per file (deduplicated by
kind + previous + observed markers, first occurrence wins).
