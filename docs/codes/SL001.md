# SL001: Malformed record

## Overview

- **Code**: `SL001`
- **Category**: `syntax`
- **Default Severity**: `error`
- **Default Repairability**: `manual`
- **Summary**: Report record ordinal plus line and byte offset where available.

## Invariant

Every non-empty nonterminal line in a session stream must decode as valid UTF-8, strictly comply with the max-line byte limit, contain no NUL bytes, and parse into a well-formed JSON object within recursion limits.

## Cause

A nonterminal line was corrupted, truncated mid-stream, or injected with illegal binary data (such as NUL bytes or unescaped control characters) followed by subsequent lines.

## False-Positive Notes

If a client improperly serializes multiline log messages containing unescaped raw newlines, downstream consumers will observe subsequent lines as malformed records.

## Evidence

Beyond the standard stream coordinates (`byte_offset`, `byte_end`,
`record_ordinal`), the **first** SL001 per file may carry two extra integer
fields quantifying the vendor-invisible tail (detector-depth T-01):

| Field | Meaning |
| --- | --- |
| `following_complete_records` | Count of records that parsed cleanly *after* this malformed line. |
| `following_bytes` | Bytes from this line's end to end-of-stream, minus any torn terminal region already claimed by SL002. |

A stop-at-first-error vendor loader hides everything after the first
malformed record; these counts turn "line 402 is malformed" into "line 402
is malformed — N further records / M bytes may be invisible to vendor
loaders". Keys are omitted when the tail is empty (e.g. the malformed line
is followed only by a torn terminal record), and only the first SL001 is
enriched — later malformed lines would double-count the same tail.

> Vendor caveat: whether a given vendor's loader actually stops at the first
> malformed record varies by vendor and version. SessLint reports what such
> a loader *may* hide, never what it provably does.

## Recipe or Manual Path

Nonterminal malformed records cannot be safely repaired without arbitrary synthesis or data loss; manual operator intervention is strictly required.

Policy: *Nonterminal malformed records block automated repair; cannot be overridden to deterministic.*

Salvage path: under explicit `--policy salvage --acknowledge-side-effects`, the lossy `torn-record-excision` recipe may omit exactly one malformed per-line record. It never applies to stream-level refusals (`size_limit_exceeded`) and refuses when a parsed event provably parents to the torn record's extracted id. The omission is disclosed in the plan and manifest (loss class `torn-record`), the source remains untouched, and output assurance is capped at structural validity.
