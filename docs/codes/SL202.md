# SL202: Accepted terminal output not durable

## Overview

- **Code**: `SL202`
- **Category**: `checkpoint`
- **Default Severity**: `error`
- **Default Repairability**: `manual`
- **Summary**: Runtime state indicates accepted output that the history cannot recover.

## Invariant

Terminal output accepted and displayed to the user must be durably stored in the session history.

## Cause

Assistant generated response displayed in user interface, but crash occurred before durable write to disk.

## False-Positive Notes

Draft or preview responses that were canceled by the user before acceptance.

## Recipe or Manual Path

Manual review. Resuming without durable output risks prompting duplicate actions.

Policy: *Missing accepted terminal output risks re-entering model or duplicate actions.*

## Example

```json
Metadata reports terminal message ID "msg_final" delivered, but "msg_final" is absent from event stream.
```

## Boundary and Evidence Scope (FR-044, DEV-011)

- **Events-Only Verdict Boundary**: Current SL202 verdicts are evaluated strictly over
  the canonical event stream (detecting identical sequence numbers with conflicting
  state hashes).
- **Preserved Run-State Evidence**: When runtime state and checkpoints are supplied by
  an input adapter (e.g. OpenAI Agents SDK `run_state` and `checkpoints`), SessLint
  redacts the metadata to a content-free structural projection (`keys`, `shapes`,
  `checkpoints`, `truncated`) and preserves it in finding `evidence["run_state"]`.
  Raw values and prompts are never included.
- **Future Ownership Verdicts**: Evaluating terminal-output ownership against provider
  runtime continuation states requires upstream provider semantics. This is tracked
  under research item **OPP-019** for future ownership verdicts.
