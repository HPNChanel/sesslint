# SL303: Duplicate JSON key

## Overview

- **Code**: `SL303`
- **Category**: `compatibility`
- **Default Severity**: `warning` (`error` when the duplicated key is in the
  decoding adapter's `CRITICAL_KEYS` set)
- **Default Repairability**: `manual`
- **Summary**: Record contains a duplicated object key; parsers disagree on
  which value wins.

## Invariant

Within a single JSON object, every key must appear at most once. RFC 8259
permits duplicate names but does not define their handling: Python's
`json` keeps the last value, other loaders keep the first, reject, or
merge. That silent parser disagreement is the integrity signal — two
conformant tools can read the same record and disagree on its identity,
parentage, or pairing fields.

Detection happens at record-decode time via an `object_pairs_hook`, so the
last-wins parse result is preserved while every duplicate position is
recorded. One finding is emitted per duplicated key path, capped at 16 per
record (`truncated: true` in evidence when more exist).

## Cause

Hand-edited or spliced records, buggy exporters concatenating fields,
merge tools that union objects textually, or vendor writers that append a
corrected field instead of replacing it.

## Severity Rule

- `error` — the duplicated key participates in identity, parentage,
  pairing, or continuation (the adapter's `CRITICAL_KEYS`, e.g. `id`,
  `parent_id`, `type`, `call_id`). A parser disagreement there changes the
  record's semantics outright.
- `warning` — duplicates on any other key.

## False-Positive Notes

A finding means the record text literally repeats a key — never a
suspicion. Duplicate keys are spec-legal JSON, so exporters that
intentionally rely on last-wins behavior may regard the warning as noise;
downgrade it via `ignore` in profile configuration rather than by editing
records blindly. SessLint never treats re-stated keys across *different*
records or array elements as duplicates — only keys repeated inside one
object.

## Evidence

Content-free positions and counts only — never the duplicated values:

- `key_path`: schema position (`$.id`, `$.payload.note`, `$.arr[0].k`)
- `occurrence_count`: total appearances of the key at that position
- `critical`: whether the key is in the adapter's `CRITICAL_KEYS`
- `record_index` / `record_ordinal` where available
- `truncated`: `true` when the record held more than 16 duplicates

## Recipe or Manual Path

No automated repair: choosing which occurrence wins invents record
semantics. Inspect the flagged key path, determine which value is
authoritative, and rewrite the record so each key appears once.

Policy: *Parser-divergent records are reported, never guessed.*

## Example

```json
{"id": "evt-1", "id": "evt-9", "kind": "message", "ts": "2026-09-05T12:00:00Z"}
```

yields one `error` finding naming `$.id` — Python keeps `evt-9`, but a
first-wins loader keeps `evt-1`; parent edges resolve differently under
each reading.
