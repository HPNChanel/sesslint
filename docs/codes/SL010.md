# SL010: Interleaved writer markers

## Overview

`SL010` flags a session file whose records carry **interleaved writer-identity
markers** — evidence that more than one writer process appended to the same
ledger. Concurrent writers are the corruption precondition behind dropped
writes, orphaned tool results, and ID collisions: two appends racing on one
file can silently interleave or lose records.

A writer marker is adapter-normalized metadata on each event
(`extra_fields["writer"]`): a per-process `instance` discriminator when the
vendor records one, else the application `version` build that wrote the
record. Adapters that emit no markers produce no findings — absence of
markers is never treated as proof of a single writer, and the coverage
block records `adapter-not-applicable` instead of a silent pass.

Severity is `warning`; repairability is `manual` — interleaved markers are
forensic evidence, not a defect to edit out. The engine never rewrites
markers or reorders records.

## Invariant

Within one session stream, writer markers should appear in **ordered runs**:
records written by writer A, then optionally records written by writer B.
A marker that *reappears* after a different marker (A → B → A) proves the
writers interleaved appends on one file.

- **Interleaved markers fire once**: at most one `SL010` per file, anchored
  to the first line where a marker reappears after a different marker —
  bounded noise by design.
- **A clean ordered transition stays clean**: A* → B* (every A record
  precedes every B record) is a legitimate mid-session upgrade or a
  takeover — a single writer finishing, then another continuing. No
  finding.
- **A single writer, or absent markers, stays clean**: fewer than two
  distinct markers can never interleave.
- **Version-interleaving alone is sufficient**: two interleaved application
  versions mean two different builds appended to the same ledger —
  impossible for one process that did not downgrade mid-flight. When the
  vendor also records a per-instance discriminator it takes precedence over
  version.

Evidence is structural only: `distinct_writer_count`, `transition_count`,
`first_interleave_line`, and `writer_hashes` — sorted 8-hex SHA-256
prefixes of the marker strings. Marker values are near-public version
identifiers, but hashing keeps the content-free contract uniform and still
lets operators diff writer sets across files. Raw marker strings never
appear in findings, reports, or logs.

## Cause

- Two agent processes writing the same session ledger concurrently —
  parallel invocations, a crashed-and-restarted process overlapping with
  its successor, or non-atomic append races (observed upstream as
  interleaved `version` markers in a single `.jsonl`).
- A session file assembled or spliced from two different writers' outputs
  (manual merge, copy-on-resume) — same structural signature, different
  provenance story.
- Deliberate multi-process pipelines where a supervisor and a worker both
  append records — legitimate architecture, still worth knowing about
  because downstream integrity checks (SL101, SL003) may fire as
  consequences.

## False-Positive Notes

- **Version markers are build identities, not process identities.** An
  interleaved version pair proves the *builds* interleaved, which a single
  process cannot produce — but it cannot distinguish "two concurrent
  processes" from "one file assembled from two files' outputs". The finding
  reports interleaving, not a specific cause.
- A vendor that bumps its version string per-write (rather than
  per-release) would make a single writer look like many — no such vendor
  behavior is verified today; markers come only from fields documented as
  application-build versions.
- Mid-session upgrade A* → B* is the expected common case and stays clean
  by construction — only reappearance proves interleaving.
- Records that emit multiple canonical events share one source line and one
  marker; the detector deduplicates per (line, marker) so a single
  multi-event record cannot fake a transition.

## Recipe or Manual Path

`SL010` has no automatic repair — markers are provenance evidence and
rewriting them would fabricate history.

- Check for **consequence findings** in the same file (SL101 orphans,
  SL003 duplicates, SL004 missing parents): concurrent writers leave
  exactly these artifacts. Remediate the concrete defects, not the marker
  pattern.
- If two live processes genuinely share the ledger, serialize them —
  one writer per session file, or vendor-level session forking.
- If the file was manually merged from two sources, treat it as two
  sessions: split by writer runs, or keep it read-only as forensic
  evidence.
- `writer_hashes` lets operators confirm two files share a writer
  (identical hash sets) without exposing the version strings themselves.

## Example

markers: `2.0.9` writes records 1–2, `2.1.0` writes record 3, then `2.0.9`
writes record 4 — an A → B → A interleave:

```text
sl010_interleaved.jsonl: WARNING SL010 — Interleaved writer markers in
session file for record u4
[distinct_writer_count=2, transition_count=2, first_interleave_line=4,
 writer_hashes=(<hash-8>, <hash-8>)]
```

The sibling `sl010_upgrade.jsonl` (A* → B* ordered transition) and
`sl010_single_writer.jsonl` (one version throughout) both stay clean, as
does every non-Claude fixture — adapters that emit no writer markers are
coverage-skipped, not flagged.
