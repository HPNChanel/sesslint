# SL305: Provider-incompatible record shape

## Overview

`SL305` flags a Codex rollout file containing records whose shape sits
outside the **official replay vocabulary** — the file parses cleanly,
but the provider's resume path rejects it. This is the
"file parses, provider rejects" class: a third-party
Responses-compatible provider may persist record shapes that are legal
JSONL and readable by Codex, yet invalid when the same history is
replayed against the official API.

The cited signature is openai/codex#36551: a third-party provider
writes `reasoning` items with `payload.content` set to a
`reasoning_text` parts array, while the official Responses API expects
`reasoning.content` to be `null` (replay fails with `Expected an array
with maximum length 0`).

This is a Codex-rollout-scoped rule: the adapter normalizes the
`reasoning_content_shape` marker (`"absent" | "null" | "array" |
"other"`) into `extra_fields["codex"]`, and the check runs only when
the detected format is `codex-rollout` — other adapters produce zero
findings and a coverage `adapter-not-applicable` skip.

Severity is `warning`; repairability is `manual` — provider-shape
compatibility is a replay-target contract. The engine never rewrites
records to match the vocabulary.

## Invariant

For a codex-rollout stream, `reasoning` response items must carry
`content` absent or `null`:

- **`reasoning-content-non-null`**: a `reasoning` item whose `content`
  key holds a non-null value (array or otherwise) is outside the
  official replay vocabulary — openai/codex#36551: `Invalid
  'input[x].content': array too long. Expected maximum length 0`.
  One finding per file, anchored to the first offending record.

Evidence is structural only: `shape_violation`, `item_family`,
`item_count`, `first_ordinal`, plus bounded *declared* provider context
(`declared_provider_hash` — sha256-8 of `session_meta.model_provider`,
`declared_originator_present`) — never payload text, never the raw
provider name, and never asserted as provenance.

## Cause

- The session was written while Codex was configured against a
  third-party Responses-compatible provider whose `reasoning` items
  carry inline `reasoning_text` parts instead of `encrypted_content`
  (openai/codex#36551, label `custom-model`). After switching back to
  the official endpoint, resume replays the persisted items and the
  official API rejects them.
- A splice mixing official and provider-foreign reasoning items (the
  foreign items typically also lack `encrypted_content` — see the
  SL206 `missing-required-field` boundary note below).

## False-Positive Notes

- **Open-world caveat.** "Foreign-shaped" can never be proven — only
  "not in the known official replay vocabulary". A future official
  shape change could invalidate the vocabulary entry; severity stays
  `warning`, and every vocabulary rule carries an upstream citation.
- **Self-reported provider only.** `model_provider`/`originator` are
  writer-declared config strings, not verified provenance — the
  finding reports declared context as a hash, never as a claim that a
  foreign provider wrote the file.
- **Known shapes only.** Absent or novel shapes stay silent; unknown
  is never treated as foreign. The vocabulary is additive per citation.
- **`content: null` is official.** Only *non-null* `content` values
  fire — the official shape itself carries the key with a null value.

## Recipe or Manual Path

`SL305` has no automatic repair — rewriting `content` to `null` (the
vendor-documented workaround) discards provider-persisted reasoning
text and changes what the replayed context contains; that is a
content/semantic mutation outside the conservative repair contract.

- Preserve the file as evidence; resume under the provider that wrote
  it, or start a fresh thread and reference the old session by id.
- The vendor-documented manual path (after backup): for each
  `response_item` whose `payload.type == "reasoning"` and
  `payload.content` is an array, rewrite `content` to `null` — then
  resume against the official API. SessLint performs no rewrite.

## Boundary vs SL206 / SL304

- **SL206 `missing-required-field`** fires only on *mixed*
  `encrypted_content` presence across reasoning items. A uniformly
  foreign file (every reasoning item has non-null `content`, none has
  `encrypted_content`) is silent under SL206 — SL305 carries the
  signal. A spliced file can fire both.
- **SL304** detects *intra-file* schema drift; a uniformly foreign
  file has no internal drift point.

## Example

`fixtures/adapters/codex/sl305_foreign_reasoning.jsonl` carries two
`reasoning` items with `content` arrays and a declared
`model_provider`:

```text
sl305_foreign_reasoning.jsonl: WARNING SL305 — Record shape outside the
replay vocabulary on line 3 for record <synthetic-id>
[shape_violation=reasoning-content-non-null, item_family=reasoning,
 item_count=2, first_ordinal=2, declared_provider_hash=03520cc4,
 declared_originator_present=true]
```

The sibling `sl305_null_content.jsonl` (official `content: null` and
absent `content` shapes) stays clean; `sl305_mixed_splice.jsonl` fires
SL305 alongside SL206 `missing-required-field`.
