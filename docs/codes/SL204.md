# SL204: Token usage arithmetic inconsistency

## Overview

- **Code**: `SL204`
- **Category**: `accounting`
- **Default Severity**: `warning`
- **Default Repairability**: `manual`
- **Summary**: Cumulative token-usage marker contradicts the window's usage sum.

## Invariant

Within one accounting window, a cumulative token-usage marker must equal
the previous marker's totals plus the sum of per-event usage
contributions — exact integer equality, per counter. A divergence means
the ledger's arithmetic cannot be self-consistent: records were dropped,
spliced, or the totals were rewritten.

Adapters normalize vendor usage fields into
`SessionEvent.extra_fields["usage"]` with two slots: `contribution`
(this record's delta — Codex `usage`) and
`cumulative` (running-total marker — Codex `thread_token_usage`). The
marker record's own contribution counts toward the window it closes.
Codex `turn_token_usage` is the *turn-scoped* cumulative — summing it as
a contribution double-counts every marker, so it is never mapped.

A `compaction_boundary` resets the epoch: contributions accumulate fresh
and the first marker after a boundary establishes a new baseline
unchecked, since counters may legitimately restart or continue across
compaction.

## Cause

Torn writes or truncation dropping usage records, splice/merge tools
reconciling totals incorrectly, partial compaction rewriting cumulative
markers without adjusting earlier contributions, or hand-edited
counters.

## False-Positive Notes

Vendors may emit usage fields whose "cumulative" semantics are not
per-session (e.g. per-thread vs per-turn). Only the observed Codex
`token_usage_record` shape is mapped today — `usage` as contribution,
`thread_token_usage` as cumulative — so unmapped shapes never reach the
check. Markers lacking `usage` emit no slot at all: a cumulative without
a contribution stream is not arithmetically checkable and would
false-fire on vendor-normal growth. Counter values that are not
non-negative integers are ignored per key rather than flagged.

## Evidence

Content-free integers and coordinates only:

- `record_id`: the divergent marker record
- `expected_total` / `observed_total`: sums over the marker's counters
- `mismatched_key_count`: how many counters disagreed
- `window_start_index` / `window_end_index`: stream indices bounding
  the reconciled window

## Recipe or Manual Path

No automated repair: correcting a divergent total requires knowing which
side of the ledger is corrupt — the marker, the contributions, or both.
Inspect the flagged marker and its window, then reconcile by hand.

Policy: *Accounting evidence is reported, never rewritten.*

## Example

```text
usage              = {input: 3, output: 2}    # this record's contribution
thread_token_usage = {input: 99, output: 7}   # baseline was {10, 5}
```

Expected `{input: 13, output: 7}` — the input counter is inflated by 86.
One `warning` naming the marker record with `expected_total: 20`,
`observed_total: 106`, `mismatched_key_count: 1`.
