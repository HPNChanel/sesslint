# SL011: Record size anomaly

## Overview

`SL011` flags the single largest record in a file when its byte size is an
extreme outlier relative to **the file's own size distribution**. It is the
content-free tripwire for "a giant blob got spliced into this session" —
embedded dumps, base64 payloads, accidental log captures.

Severity is `info` (the lowest level — it never trips `--fail-on warning`
defaults); repairability is `manual` — a human decides whether the blob is
legitimate. The engine never drops or truncates the record.

## Invariant

For a file whose record-size distribution is meaningful (≥ 8 records), no
record should exceed `max(median × 20, 256 KiB)` — where `median` is the
upper median of the file's own record byte sizes.

- The check is **relative**, never absolute: legitimate large records exist
  (real rollout outputs reach ~1.5 MiB — the reader line cap already handles
  absolute limits). A file of uniformly large records stays clean because
  its own median raises the threshold.
- Files with fewer than 8 records skip the check entirely — the coverage
  block records `adapter-not-applicable` ("fewer than 8 records — size
  distribution not meaningful").
- `codex-rollout` files skip the check entirely — Codex envelopes mix
  byte-scale metadata records with multi-MiB bulk payloads
  (`event_msg`/`compacted`/`response_item`) by design, so on real
  corpora the outlier fires on ~84% of files and carries no signal.
  Coverage records `adapter-not-applicable` ("record-size variance is
  vendor-normal on codex-rollout envelopes").
- At most one finding per file: the largest outlier only — bounded noise by
  design. Deterministic: integer median via sorted selection; the ratio is
  computed from the file's own data.

Evidence is numbers only: `record_index`, `record_bytes`,
`file_median_bytes`, `ratio` — no payload content.

## Cause

- A spliced or injected blob inside an otherwise normal session — the
  classic corruption signature this rule exists to catch.
- An embedded file dump, base64 payload, stack trace capture, or accidental
  log paste inside one record.
- Legitimate heavy records (large tool outputs, image references) in a file
  that is otherwise small — the relative formula tolerates these only up to
  the K×median margin.

## False-Positive Notes

- Bimodal files (many small + many large records) can produce a low median
  that makes a legitimate large record look anomalous — the `max(median×K,
  floor)` formula is deliberately conservative, but residual positives are
  expected at info severity.
- Very small files (< 8 records) never run the check — see the coverage
  skip entry rather than expecting silence to mean "checked".
- Uniformly large files (e.g. rollout exports where every record is ~1 MiB)
  stay clean by design: the median scales the threshold.

## Recipe or Manual Path

`SL011` is informational — there is no automatic repair. Inspect the flagged
record (`record_index` + `record_bytes` in evidence):

- If the blob is a foreign splice, remove the record by hand and re-check —
  SessLint does not rewrite source ledgers.
- If it is legitimate session content, no action is needed; the finding is
  a tripwire, not a defect verdict.
- If it recurs across files, consider `--ignore SL011` in
  the profile rather than per-file edits.

## Example

`fixtures/checks/sl011_outlier.jsonl` holds nine ~150-byte records and one
~300 KiB record:

```text
outlier.jsonl: INFO SL011 — Record is a byte-size outlier within this file
[record_index=9, record_bytes=300156, file_median_bytes=156, ratio=1924.077]
```

The sibling `sl011_uniform.jsonl` (ten uniform records) and
`sl011_small.jsonl` (five records — below the distribution minimum) both
stay clean.
