# SL401: Unresolved cross-file link

## Overview

`SL401` flags broken resume/continuation links **between** session files. A
file that declares a `parent_session_id`, `resume_from`, `forked_from_id`,
`parent_thread_id`, or `resume_head_id`-style pointer is claiming to continue
a predecessor artifact; when that predecessor cannot be identified inside the
scanned set, the continuation chain is broken.

This is the first scan-layer (cross-file) detector: it is emitted on the
**referencing** file's `FileResult` during `sesslint scan` and is never
produced by single-file `sesslint check` — a single file cannot prove the
absence of its link target.

Adapters surface declared pointers as bounded structural metadata
(`session_ref` / `head_ref` links) during parsing; extraction is read-only,
deduplicated, and capped at 16 links per file.

## Invariant

For every scanned file, each declared resume link must resolve unambiguously
inside the scan root:

- `session_ref` targets resolve against declared `session_id` values and
  filename stems (bare ids) — or against scanned basenames when the target is
  spelled like a path. For Codex rollouts the linkable identity is
  `session_meta.id` (the thread uuid — equal to the `rollout-<ts>-<uuid>`
  filename suffix and the target of `parent_thread_id`/`forked_from_id`
  spawn links); the separate `session_id` field is not the link identity.
  The filename uuid is indexed too, so a link still resolves when the
  parent's `session_meta` is torn, and only the *first* `session_meta`
  contributes identity (later ones are inherited parent context).
- `head_ref` targets resolve against per-file tip event ids (the last event
  id of each scanned file).
- A pointer matching the referencing file's own session identity is a
  self-reference, not a cross-file link — it is satisfied by definition.

Resolution outcomes:

- Exactly one candidate → resolved silently (no finding).
- More than one candidate → `SL401` warning with `resolution: "ambiguous"`.
- Zero candidates on a bare-id `session_ref` → `SL401` warning with
  `resolution: "missing"` — the scan enumerated every session id and stem in
  the set, so absence is provable.
- Zero candidates on a path-like `session_ref` or on a `head_ref` → `SL401`
  info with `resolution: "unresolved"` — a narrower scan cannot prove the
  target does not live outside the root, and a head event could sit mid-file
  (only tips are indexed).

## Cause

- A continuation file was exported, moved, or scanned without its
  predecessor — e.g. a 3-file chain scanned with the middle file removed.
- Two scanned files declare the same `session_id` (copies, forked exports),
  making the resume target ambiguous.
- The link names a path outside the scan root — a deliberately narrower scan.
- A forged or hand-edited ledger may invent resume pointers that nothing
  satisfies.

## False-Positive Notes

- Scanning a deliberately narrowed subtree: links pointing outside the root
  report as info-level `unresolved`, not warnings — widen the scan root to
  resolve them.
- Files that share a `session_id` legitimately (e.g. byte-copied artifacts)
  produce `ambiguous`; deduplicate or ignore the rule per profile.
- `head_ref` links only resolve against file tips by design — a link at a
  mid-file event reports `unresolved` rather than `missing` because the scan
  cannot prove the event is absent.

## Recipe or Manual Path

`SL401` is **manual** repairability: the correct predecessor file must be
supplied by the user — SessLint never invents link targets.

- Re-run the scan over the common parent directory so the predecessor file is
  in scope.
- If the predecessor was deleted or never exported, treat the file as a new
  root session — the pointer is provenance noise, not corruption.
- If the link is spurious (tool wrote it but resume never happened), remove
  the pointer field by hand and re-scan; SessLint does not rewrite source
  ledgers.

## Example

`fixtures/scan/linkage/missing/` contains a two-file scan: `sess-c.jsonl`
declares `parent_session_id: "sess-b"`, but `sess-b.jsonl` was removed from
the set.

```text
sess-c.jsonl: WARNING SL401 — Cross-file resume link target is absent
from the scanned set [resolution=missing, target=sess-b]
```

Scanning the sibling `chain/` tree (with `sess-b.jsonl` present) produces no
`SL401` findings — the same child file is only flagged when its target is
provably absent.
