# SL009: Persisted secret material

## Overview

- **Code**: `SL009`
- **Category**: `structure`
- **Default Severity**: `warning`
- **Default Repairability**: `manual`
- **Summary**: Persisted record bytes contain a known secret token shape.

## Invariant

A session artifact must not persist credential material. Agent transcripts
routinely capture tool stdout, `.env` reads, serialized exceptions, and
config dumps — and those bytes are later synced into dotfile repos, shared
as bug evidence, or replayed through other providers. Every leaked token
shape that SessLint can recognize by *format alone* is flagged at the exact
record where it persists.

Detection runs on the **raw persisted bytes** of each record during the
adapter's normal streaming pass — before JSON validation — so secrets
inside malformed, truncated, or unknown-type records are still surfaced.
Detection is family-based: each family is a documented token format,
precision-weighted over recall. There is no generic entropy scanning and
no network validation of whether a token is live.

One finding is emitted per (record, family) pair. A record carrying three
AWS keys produces one `aws-access-key` finding with `occurrence_count: 3`
and three digests. Output is capped at 64 findings per file and 16 digests
per finding; totals stay exact and suppressed output is marked with
`truncated` / `overflow` evidence.

The matched secret value is **never** emitted — not in findings, reports,
stderr, SARIF, HTML, bundles, or commit messages. Only the family label,
coordinates, count, and digests survive.

## Cause

Tool output capture (a `Read` of `.env`, a shell command printing a config),
serialized exceptions embedding request headers, transcript backups or
dotfile synchronization copying session stores verbatim, and agent runtimes
persisting credential-shaped fields that downstream tooling never scrubs.

## Evidence

Content-free evidence only — never the matched bytes:

- `secret_family`: the matched family label (see table below)
- `occurrence_count`: total matches of that family within the record
- `match_sha256`: sorted SHA-256 hex digests of each distinct matched byte
  span (for `generic-credential-assignment`, of the assigned value only, so
  `token: X` and `token=X` digest identically)
- `match_len`: length in bytes of the longest matched span
- `secret_family_set`: the `SECRET_FAMILY_SET_VERSION` the match was
  detected under (currently `1`)
- `record_ordinal`, `byte_offset`, `byte_end`: record coordinates
  (`record_ordinal` is absent for single-document formats whose records do
  not map to physical byte spans)
- `truncated` / `overflow`: present when output caps suppressed further
  digests or findings

## False-Positive Notes

- `generic-credential-assignment` is the broadest family by design: fields
  named `session_token`, `csrf_token`, or similar fire when assigned a
  literal-looking value. Placeholder values (`null`, `xxxxxxxx`,
  `${VAR}`, `<VAR>`, uniform-character strings, `your-*`, and a small
  literal vocabulary) are excluded; `token_count`, `token_endpoint`,
  `secretary`, and `id_token_hint` never match because the keyword must end
  the key token immediately before the separator.
- Prefix families match the token *shape*, not its validity — an expired or
  revoked token still fires (correctly: persisted credential-shaped bytes
  are the hazard, live or not).
- `private-key-block` detects the header marker plus its first base64
  fragment when adjacent; the digest discriminates between different keys
  but the body is never inspected or stored.
- `match_sha256` of a low-entropy value (a short `generic` assignment) is
  brute-force searchable; the digest exists to *verify removal*, not to
  prove secrecy.
- Short prefixes and truncated shapes never fire (`ghp_abc`,
  `sk-ant-short`): every family enforces its documented length floor.

## Recipe or Manual Path

No automated repair — deleting or rewriting the record mutates evidence
without revoking the credential. Manual remediation:

1. **Rotate the secret** at its issuer first — deleting the transcript does
   not revoke anything.
2. Locate every occurrence via the finding's `line`, `byte_offset`, and
   `match_sha256` digest.
3. Delete or quarantine the affected artifact manually (or rotate the
   credential so the persisted copy is dead).
4. Re-run `sesslint check` and verify the digest no longer appears.

Policy: *Persisted secrets are reported with digests, never echoed, never
rewritten.*

## Sharing artifacts

<!-- next-release -->

`sesslint bundle` output is content-free, but the *source* file it
describes still carries the live secret — and pasting raw transcript
excerpts into the same issue would leak it. When a bundled source
produced SL009 findings, the bundle gains a `share_advisory` block
(`sesslint.bundle/v1`, optional): `kind`, `finding_count`, sorted
`families`, and a rotation `note`. `bundle` also prints a one-line
notice on stderr; `--strict-share` exits `1` and writes nothing when the
advisory is present, which is the recommended CI gate before artifacts
leave the machine.

## Example

```json
{"id": "evt-7", "kind": "tool_result", "payload": {"output": "ghp_…"}}
```

yields one `warning` finding at that record's coordinates with
`secret_family: "github-pat-classic"`, `occurrence_count: 1`, and the
SHA-256 digest of the matched span — the token itself never appears in any
output.
