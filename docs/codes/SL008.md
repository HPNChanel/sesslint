# SL008: Non-monotonic timestamp

## Overview

- **Code**: `SL008`
- **Category**: `graph`
- **Default Severity**: `warning`
- **Default Repairability**: `manual`
- **Summary**: Child event timestamp precedes its resolved parent's timestamp.

## Invariant

Along every causal edge (event → uniquely resolved parent), the child's
`ts` may precede the parent's `ts` by at most `timestamp_skew_ms` (default
2000). Only larger backwards differences contribute to a finding. Comparison is
per-edge only — global file order is never consulted, because sidechains
legitimately interleave their records.

## Cause

Clock changes or NTP corrections mid-session, hand-edited records, spliced
or replayed subtrees, or vendor timestamp fields carrying non-append
semantics (e.g. a server-assigned time on a later-acked record).

## False-Positive Notes

<!-- next-release -->

Legitimate clock skew is the reason this is a `warning`, not an `error`:
the default 2000 ms tolerance suppresses small concurrent-write skews. Set
`timestamp_skew_ms = 0` in `[tool.sesslint]` or use `--timestamp-skew-ms 0`
for strict ordering. One finding per file carries `count`, `max_delta_ms`
and the coordinates of the first qualifying edge.
Equality is allowed by design (same-tick parent/child stamps are common).
Edges are skipped silently — never flagged — when:

- the parent is missing (SL004 territory), or the parent id is duplicated
  (SL003 territory — no unique edge to compare);
- either endpoint's `ts` is the adapter epoch sentinel `1970-01-01T00:00:00Z`
  (substituted when the source record lacked a timestamp — a synthesized
  value cannot support a monotonicity claim);
- either `ts` fails RFC3339 parsing, or the pair mixes naive and
  offset-aware values with no reliable ordering.

## Recipe or Manual Path

No automated repair: reordering events or rewriting timestamps requires
knowing which clock was authoritative, which is exactly the unknown.
Inspect the flagged edge, decide whether the skew is benign clock drift or
evidence of splicing, and re-record or hand-edit the ledger accordingly.

Policy: *Timestamp anomalies are reported, never rewritten.*

## Example

```json
{"id": "evt-2", "parent_id": "evt-1", "ts": "2026-09-05T11:59:57Z"}
```

with `evt-1` stamped `2026-09-05T12:00:00Z` — the child precedes its parent
by 3000 ms (`ts_delta_ms: -3000`), exceeding the default tolerance.
