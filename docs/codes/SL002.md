# SL002: Torn terminal record

## Overview

- **Code**: `SL002`
- **Category**: `syntax`
- **Default Severity**: `error`
- **Default Repairability**: `deterministic`
- **Summary**: Distinguish an incomplete final append from malformed data followed by later records.

## Invariant

A session stream must terminate cleanly after a complete record. Any final non-empty line must be fully formed or flagged as an incomplete terminal append.

`SL002` is reserved for a *provable* torn append: the final non-empty line has no trailing newline, was fully buffered (within the line byte limit), and its bytes — minus any trailing NUL padding a crash can leave behind — are a proper prefix of a JSON object: text the interrupted write could still have completed, ending inside a string, number, literal or open container, possibly mid-way through a multi-byte UTF-8 sequence. Garbage, a non-object value, or a token no continuation could make valid is malformed data, not a tear. Such findings carry `"unterminated": true` in their evidence. Every other defect on the final line is `SL001`.

## Cause

The writing process was killed mid-write (SIGKILL, power cutoff, or disk exhaustion) before the trailing record could be completed and flushed with a newline. A final line whose only defect is a lone surrogate (for example `\ud800`) is the same terminal failure: one SL002 finding, and the check does not abort. The title stays `Torn terminal record`. The Why line is `line N contains an invalid Unicode character (lone surrogate, e.g. \ud800), so it cannot be parsed as a session record. The file was not truncated.` An ordinary torn append still says `Torn terminal record on line N for record …`.

## False-Positive Notes

Active live streams being tailed or read concurrently may temporarily exhibit torn terminal records if read mid-flush.

## Recipe or Manual Path

Deterministic automated repair via the `torn-terminal-record-discard` recipe, provided no irreversible side-effecting action occurred after the cut point. The recipe's `torn_terminal_record` precondition requires the `unterminated` evidence marker, so an `SL002` finding without it (an older or hand-edited plan) is refused rather than suffix-dropped.

Policy: *Only terminal incomplete records qualify; repairable by conservative suffix drop.*
