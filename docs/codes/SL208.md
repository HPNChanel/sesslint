# SL208: Compaction snapshot divergence

## Overview

`SL208` flags a Codex rollout file whose **embedded pre-compaction snapshot
disagrees with the durable item stream on a shared item id**. Codex
`compacted` records carry `guardian_history` — the vendor's own structural
snapshot of the thread at the boundary. Every snapshot item declares an id,
an item type, and (for tool items) a correlation id; the durable stream
declares the same fields for the same item ids. When both representations
exist for one id they must agree — a contradiction is provable on-disk
divergence written by the vendor itself.

This is a Codex-rollout-scoped rule: the adapter projects each snapshot
item into bounded `extra_fields["codex"]["guardian_items"]` markers
(`id`/`type`/`call_id` only, capped at 512 items per record with a
`guardian_items_truncated` flag) and each durable item's declared
correlator into `extra_fields["codex"]["call_id"]`. The check runs only
when the detected format is `codex-rollout` — other adapters produce zero
findings and a coverage `adapter-not-applicable` skip.

Severity is `warning`; repairability is `manual` — the snapshot is a
vendor-internal artifact and the check never rewrites either
representation. On a real corpus (84,917 shared items across 640
`compacted` records in 150 files) all three invariants held with zero
violations, so a firing is a meaningful anomaly, not vendor-normal noise.

## Invariant

For every item id present in **both** a `compacted` record's
`guardian_history` and the file's durable `response_item` stream, the two
declarations must agree. At most one finding per divergence kind per file:

- **`type-mismatch`** — the snapshot's declared item type differs from the
  durable record's declared type for the same id (e.g. the stream records
  `msg_t1` as a `message` while the snapshot serializes it as
  `reasoning`). Same id, two incompatible type claims.
- **`correlation-mismatch`** — the snapshot's declared correlator differs
  from the durable record's declared correlator, including presence
  disagreement (one side declares a correlation id the other side lacks).
- **`future-item`** — the snapshot cites an item whose **only** durable
  appearance sits strictly after the `compacted` record: the snapshot
  claims history the stream had not yet written. The earliest durable
  occurrence is the reference, so later id reuse cannot mask the
  divergence or false-flag a legitimately rewritten item.

Evidence is structural only: `divergence`, `item_id` (the bounded vendor
identifier class already exposed as record ids), declared type
vocabulary, declared correlators, stream indexes, and `occurrences` —
never item content, never `input`/`output`/message text.

Deliberately **not** checked (fail closed):

- **Snapshot-only ids** — a snapshot may legitimately carry inherited
  parent context absent from this file's stream; in a real corpus every
  observed snapshot-only id resolved to a sibling rollout's stream.
- **Intra-snapshot pairing** — snapshots are bounded rolling windows
  (observed lengths cluster at 50–250 item caps); an edge-truncated
  output without its call is vendor-normal.
- **Items absent from the snapshot** — compaction legitimately drops
  history; a missing snapshot entry proves nothing.

## Cause

- A compaction writer bug serializing an item under the wrong type or
  correlator inside `guardian_history` — the snapshot diverges from the
  durable record it claims to mirror.
- A mid-session splice or rewrite producing an id whose snapshot
  declaration contradicts its durable one.
- Snapshot assembly reading ahead of the durable cursor — the embedded
  history cites items the stream had not yet persisted (`future-item`).

## False-Positive Notes

- **Version-dependence**: `guardian_history` is a vendor-internal field;
  its serialization contract is inferred from observed rollout behavior
  (100% field agreement across 84,917 shared items). If a future vendor
  version legitimately transforms items inside snapshots — relabeling
  types or rebasing correlators — the same bytes would read as
  divergence. Severity stays `warning`, not `error`.
- The check compares **declared** fields on both sides; adapter
  normalization artifacts (synthetic ids, correlator fallbacks) are
  excluded from the stream side so only vendor-written values compare.
- Duplicate ids inside the stream resolve to the **first** occurrence —
  the earliest durable claim — so post-boundary rewrites under a reused
  id cannot fabricate a `future-item` or type claim.
- Truncated projections (`guardian_items_total` > 512) still verify every
  projected item; unprojected tail items reduce coverage, never
  soundness — the check only flags what it can prove.

## Recipe or Manual Path

`SL208` has no automatic repair — choosing which representation is
authoritative edits evidence toward a contract the file never satisfied.

- `type-mismatch` / `correlation-mismatch`: preserve both representations
  as evidence. The durable stream remains the replay source of truth;
  the divergent snapshot marks the compaction boundary as suspect —
  inspect sibling rollouts for the same item ids before trusting
  post-compaction state.
- `future-item`: the snapshot was assembled from state the stream had
  not written — treat the whole `compacted` record as unreliable and
  check for a crash/splice around that boundary (SL001/SL206 territory).

## Example

`fixtures/adapters/codex/sl208_type_mismatch.jsonl` records `msg_t1` as a
`message` response item while the `compacted` record's snapshot declares
the same id as `reasoning`:

```text
sl208_type_mismatch.jsonl: WARNING SL208 — Compaction snapshot item type
disagrees with the durable stream on line 5 for record <synthetic-id>
[divergence=type-mismatch, item_id=msg_t1, occurrences=1,
 snapshot_item_type=reasoning, stream_item_type=message]
```

The sibling `sl208_correlation_mismatch.jsonl` (snapshot `call_zzz` vs
stream `call_c1`) and `sl208_future_item.jsonl` (snapshot cites
`msg_f9`, first written after the boundary) each fire their own
divergence; `sl208_healthy.jsonl` — snapshot and stream in full
agreement — stays clean.
