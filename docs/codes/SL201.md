# SL201: Checkpoint/history divergence

## Overview

- **Code**: `SL201`
- **Category**: `checkpoint`
- **Default Severity**: `error`
- **Default Repairability**: `manual`
- **Summary**: Serialized continuation state and durable records disagree.

## Invariant

Serialized checkpoint state must match the historical record of events up to the checkpoint offset.

## Cause

Checkpoint saved prior to event log flush, or history truncated/modified after the checkpoint was created.

## False-Positive Notes

None. Divergence prevents reliable replay or resumption.

## Recipe or Manual Path

Manual review. Rebuilding checkpoint from history or reverting history to checkpoint requires operational context.

Policy: *Continuation divergence invalidates subsequent replay state.*

## Example

```json
Checkpoint states 10 events processed; history contains only 8 events.
```

## Boundary and Evidence Scope (FR-044, DEV-011)

- **Events-Only Verdict Boundary**: Current SL201 verdicts are evaluated strictly over
  the canonical event stream (detecting missing establishing checkpoints upon resumption,
  consecutive sequence jumps > 1, and missing state hashes).
- **Preserved Run-State Evidence**: When runtime state and checkpoints are supplied by
  an input adapter (e.g. OpenAI Agents SDK `run_state` and `checkpoints`), SessLint
  redacts the metadata to a content-free structural projection (`keys`, `shapes`,
  `checkpoints`, `truncated`) and preserves it in finding `evidence["run_state"]`.
  Raw values and prompts are never included.
- **Future Ownership Verdicts**: Evaluating deep continuation-step ownership between
  runtime state variables and event history requires upstream provider semantics.
  This is tracked under research item **OPP-019** for future ownership verdicts.
